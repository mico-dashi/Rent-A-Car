# White-label and multi-tenancy

## Commercial modes

| Mode | URL | How it works |
|---|---|---|
| **A — SaaS** | `client.myplatform.com` | `create_tenant` inserts a verified platform subdomain `<slug>.<root_domain>`. Wildcard DNS and TLS cover it automatically. |
| **B — Premium white-label** | `clientdomain.com` | The tenant adds a domain (`tenant_domains`, status `PENDING_VERIFICATION`). The platform verifies DNS, then marks it `VERIFIED`. See [DEPLOYMENT.md#custom-domains](DEPLOYMENT.md#custom-domains). |
| **Branded mobile app** (enterprise, optional) | App Store / Play listing under the tenant's name | `clients/<slug>/config.ts` plus EAS profiles. Same source code. |

The web app resolves the tenant on every request from the `Host` header, using `resolve_tenant(hostname)`. Only `ACTIVE` tenants with a `VERIFIED` domain resolve. Everything else returns 404.

## Per-tenant branding

Stored in `tenant_branding`:

| Setting | Notes |
|---|---|
| Colours | primary, secondary, background |
| Fonts | heading and body font names |
| Logos | light and dark variants |
| App icon and splash | used by branded app builds |
| Hero image | storefront header |
| Headline, subheadline, about text | storefront copy |
| Contact details | shown in the storefront |
| Social links, FAQ | shown in the storefront |
| Email sender | sender name and footer |
| Default theme | light, dark or system |
| "Powered by" notice | can be removed (plan feature `white_label_removal`) |

Themes are generated by `buildTheme()` in `@rental/design-tokens`:
- A tenant background that would break text contrast in dark mode is replaced with the default black.
- `accessibleButton()` darkens the brand colour just enough to keep button labels at WCAG AA (4.5:1). Every brand colour is tested.

## Adding a new tenant

**Self-serve.** A signed-in user calls `create_tenant(slug, displayName, legalName, country, currency, language, timezone)`. That is onboarding step 1. It creates, in one transaction:
- the tenant, settings and branding
- an owner membership
- a trial subscription on the default plan
- the platform subdomain

The tenant starts as `PENDING_APPROVAL`, unless `platform_settings.tenants_auto_approve` is `true`. A super admin then sets it to `ACTIVE`, the only state that is publicly visible.

**By a platform admin.** Do the same as a platform admin, or insert the rows with the service role.

The 11-step onboarding wizard in the dashboard (`/onboarding` for step 1, then `/t/<slug>/onboarding`) tracks progress in `tenant_settings.onboarding_step` and `onboarding_data`, so owners can save and continue later.

## Universal app tenant discovery

The default is one universal iOS app and one universal Android app. They find the tenant in one of these ways:

| Method | How it works | Status |
|---|---|---|
| Tenant code | For example `APEX01` (`tenants.tenant_code`), entered in the app | Implemented |
| Invite / deep link | `rentalplatform://t/<slug>` | Implemented |
| Universal link | `https://app.myplatform.com/t/<slug>` (configured in `associatedDomains` / Android intent filters) | Implemented |
| QR code | Encodes the universal link above | Implemented |
| Custom-domain links | Tenant domains listed in a branded client's `associatedDomains` | Implemented |
| Location discovery | "Find companies near me" in the universal app (`nearby_tenants`). Off by default: enable the `location_discovery` flag for the platform, a plan or individual tenants. The user's location is only asked for on tap and never stored | Implemented |

After a tenant is selected, the app loads its branding, fleet, policies, currency and language through `resolve_tenant`. The choice is persisted in SecureStore. Branded builds lock to their tenant and cannot switch.

## Adding a white-label client

1. Copy `clients/apex-drive` to `clients/<client-slug>` and edit `config.ts`:
   - `tenantId` and `tenantSlug`, `appName`, `scheme`
   - `bundleIdentifier` and `androidPackage` (these must be unique)
   - icon, adaptive icon and splash paths
   - colours, support email, website domain, `associatedDomains`
2. Register the client in `clients/index.ts`.
3. Add EAS profiles `<client>-preview` and `<client>-production` in `apps/mobile/eas.json`, each with `APP_VARIANT=<client-slug>`.
4. Run `node apps/mobile/scripts/check-variants.mjs`. It fails on unknown variants or duplicate identifiers.
5. Create the app in App Store Connect and Google Play under the **client's own developer account** (recommended), or yours with their authorization.
6. Build with `eas build --profile <client>-production --platform all`.
7. Host `apple-app-site-association` and `assetlinks.json` on the client's domains for universal and app links.

## App-store strategy

Apple's guideline 4.3 (spam) and 4.2.6 (template apps) reject many near-identical apps.

- **Default:** do not publish a separate app per tenant. Ship the universal app, with tenant-aware theming and deep links.
- **Branded builds:** only for enterprise clients. Publish them under the client's own developer account, with enough distinct value, such as client-specific features, content and support.
- Google Play has similar repetitive-content policies.

This is guidance, not legal advice. Review the current store policies before each submission.
